# WK-192: удаление учётной записи — проверка перед ревью

## Question

Удаляется ли после удаления аккаунта всё, что связано с пользователем (БД, файлы, токены у
провайдеров, сессии на всех устройствах, память процесса), надёжно ли это при сбоях, и не
нарушает ли удаление обязательных сроков хранения.

## Current state

Реализация в PR #156: `DELETE /api/stream/account/me` (пароль), `DELETE /api/admin/users/:id`
(админ, повтор email), [account-deletion-service.ts](../../apps/api/src/services/account-deletion-service.ts),
очередь внебазовой очистки [pending-cleanup-service.ts](../../apps/api/src/services/pending-cleanup-service.ts).
Инвентаризация ПДн — [personal-data-audit.md](personal-data-audit.md) (WK-191, ветка `feat/191`).

## Findings

Проверено кодом и тестами (`apps/api/src/__tests__/account-deletion-wk192.test.ts`), UI — в
браузере (Chromium, 1920×1080 и 390×844) против локального API.

1. **Сессии.** Access JWT живёт до 1 ч и подписью не отзывается, поэтому до проверки токен
   удалённого аккаунта проходил `authenticateStreamUser`/`authenticateCompanionSession`.
   Записать данные он не мог (FK), но, например, наполнял кеши в памяти и давал 500 вместо 401.
   **Исправлено:** обе middleware проверяют существование аккаунта (один запрос по PK) и отвечают
   401. Refresh-токены удаляются каскадом → `/auth/refresh` = 401. Тест: два устройства, оба
   теряют доступ сразу. Legacy-токен Companion хранится в строке пользователя — исчезает с ней.
2. **CSRF.** Неприменимо при текущей модели: cookie нигде не используются (ни API, ни сайт),
   авторизация — заголовок `Authorization` из `localStorage`, который чужой сайт подставить не
   может; запрос с этим заголовком и JSON-телом требует CORS preflight, а CORS — allowlist без
   `credentials`. Дополнительно: самоудаление требует пароль, админское — email цели. Если
   refresh переедет в cookie (рекомендация WK-191), CSRF придётся решать заново
   (`SameSite=Strict` + проверка `Origin`).
3. **Сбои после удаления из БД.** Было: unlink и revoke «best-effort» без повтора — при сбое
   файл/токен оставались, а сведения о них терялись вместе со строкой. **Исправлено:** задачи
   (`upload` — случайное имя файла, `twitch_revoke` — пара токенов связи) пишутся в
   `pending_data_cleanups` в той же транзакции, что `DELETE`, выполняются сразу после commit, при
   сбое — повтор с экспоненциальной задержкой (1 мин … 6 ч). Sweeper запускается при старте
   backend и далее раз в 5 минут, поэтому задачи переживают рестарт (проверено тестом). Задачи
   идемпотентны: отсутствующий файл и мёртвый токен считаются выполненными. После 12 попыток или
   7 дней — `error`-лог `Data cleanup given up` (id, вид, число попыток; без токена), payload
   (токен) стирается, строка остаётся «надгробием» с `gave_up_at`. Количество окончательных
   сбоев: `dataCleanups.failed` в `GET /api/admin/usage-stats`, при ненулевом значении — строка
   на `/admin`; вручную — `SELECT COUNT(*) FROM pending_data_cleanups WHERE gave_up_at IS NOT NULL`.
   Email и иные ПДн в очередь не попадают. EventSub останавливается до commit, кеши в памяти
   чистятся после commit и ещё раз через 2 минуты (запрос, прочитавший связь до удаления, мог
   успеть их наполнить). Память процесса не переживает рестарт, поэтому для неё достаточно
   таймера.
4. **Гонка с загрузкой файла.** Если загрузка шла во время удаления, финальный файл уже был
   переименован, `INSERT` падал по FK, а контроллер удалял только временный путь — файл
   оставался сиротой. **Исправлено** в обоих upload-контроллерах.
5. **Данные без `stream_user_id`.** `quiz_viewer_scores` (через `stream_sessions`),
   `quiz_answers` (через `quiz_rounds`) — каскад, проверено тестом. Все FK на `stream_users`
   — `ON DELETE CASCADE` (тест по `information_schema`, новая таблица без каскада его уронит).
   Файлы — только два вида (`stream_overlay_reference_backgrounds.filename`,
   `stream_queue_settings.settings.webcamImageUrl`). В памяти по `streamUserId`: Twitch
   (чат/аудитория/события), OBS-команды, cooldown Dota-sync, кеш статуса интеграций оверлея —
   чистятся. Кеши OpenDota/PUBG/Steam-профилей ключуются игровым id/ником, а не аккаунтом, и
   живут минуты — не трогаем. Логи PM2 содержат `streamUserId` — вне задачи (WK-196).
6. **Сроки хранения.** Категорий с самостоятельным основанием хранения после удаления в
   продукте нет: платежей, договоров с бухгалтерскими документами, обязательных журналов нет;
   донаты DonationAlerts — данные третьих лиц, полученные для оверлея стримера, а не платёжные
   документы оператора. Логи и бэкапы удаляются по своим срокам (WK-196; бэкапов сейчас нет —
   readiness-документ WK-191). Подтверждение исполнения запроса — строка лога
   `Stream account deleted` с id и инициатором, без email. **Юридически не проверено** —
   вопрос для юриста вместе с остальными из WK-191.
7. **DonationAlerts** не имеет публичного эндпоинта отзыва токена — токены удаляются только у
   нас.
8. **Twitch revoke.** Вызов соответствует документации: `POST https://id.twitch.tv/oauth2/revoke`,
   form-urlencoded `client_id` + `token` (access-токен); 200 — отозван, 400 `Invalid token` — уже
   недействителен, 404 `client does not exist` и прочее — повтор. Документация описывает отзыв
   только access-токена, а refresh-токены confidential-клиента **не истекают**. Поэтому после
   отзыва access-токена refresh-токен погашается через `oauth2/token`: 400/401 — он мёртв (лог
   `Twitch tokens revoked`, `refreshTokenDead: true`); если он ещё жив — полученный новый
   access-токен тоже отзывается, а в лог пишется `warn` «refresh token was still valid after
   access revoke». Так на production видно фактическое поведение Twitch. **Тесты — на моке, и
   это не доказательство отзыва на стороне Twitch**; живая проверка — на тестовом аккаунте после
   релиза.
9. **Нагрузка проверки авторизации.** `SELECT 1 FROM stream_users WHERE id = $1` — Index Only
   Scan по `stream_users_pkey` (на 13 строках планировщик выбирает Seq Scan, с выключенным
   seqscan — индекс). Самый частый клиент — опрос чата Companion раз в 1,5 с; события Twitch идут
   через исходящий EventSub WebSocket сервера и middleware не проходят. Кеша существования нет:
   он вернул бы окно, в котором удалённый access-токен снова работает.

## Options

Для п. 3: (а) best-effort без повтора — проще, но теряет токены при сбое; (б) отзывать до
удаления и не удалять при сбое — нарушает право на удаление из-за чужого сбоя; (в) очередь в
той же транзакции — выбрано.

## Recommendation

Влито (PR #156) и выпущено. Остаётся ручная проверка на production (ниже).

### Ручная проверка на production

Только на отдельном тестовом аккаунте, **не** на основном аккаунте администратора.

1. Зарегистрировать тестовый аккаунт (`/stream/register`), войти в Companion этим же аккаунтом
   на втором устройстве (или во втором браузере войти на сайт).
2. Привязать Twitch тестового канала (Companion → интеграции), загрузить фон редактора.
   Проверить, что приложение видно в Twitch → Settings → Connections.
3. `/account` → «Удалить аккаунт»: неверный пароль → «Неверный пароль.»; верный → переход на `/`.
4. Проверить: вход с этим email — «Неверный email или пароль»; Companion/второй браузер теряют
   сессию при следующем запросе (401 → выход); ссылка на загруженный фон (`/uploads/…`) — 404
   (с учётом кеша браузера).
5. **Twitch:** приложение исчезло из Twitch → Connections. В логах API (PM2) для id аккаунта —
   `Stream account deleted` и `Twitch tokens revoked` с `refreshTokenDead: true`. Если вместо
   этого `warn` «refresh token was still valid after access revoke» — Twitch не гасит
   refresh-токен при отзыве access-токена; это не ошибка (новый access-токен тоже отозван), но
   повод проверить Connections вручную.
6. `/admin` (как администратор): строки «Не завершены очистки после удаления данных» нет;
   `GET /api/admin/usage-stats` → `dataCleanups: { pending: 0, failed: 0 }` через несколько
   минут после удаления.
7. Админское удаление — на втором тестовом аккаунте: `/admin/<id>` → «Удалить пользователя» →
   ввести email → после удаления возврат на `/admin`, пользователя нет в списке.
