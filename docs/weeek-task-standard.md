# Стандарт создания задач Weeek

Каждая новая задача должна оформляться в едином формате.

## Структура задачи

### 1. Название

* Короткое и понятное.
* Описывает конечный результат, а не способ реализации.
* Избегай технических деталей, если они не являются сутью задачи.

### 2. Контекст

Кратко опиши текущую ситуацию.

Ответь на вопрос:

> Почему появилась эта задача?

Не пересказывай историю проекта — только необходимый контекст.

### 3. Мотивация

Объясни, какую проблему решает задача и почему она важна.

Если задача является частью более крупной инициативы — упомяни это.

### 4. Цель (Goal)

Опиши, каким должен стать продукт после выполнения задачи.

Фокусируйся на результате для пользователя или проекта, а не на реализации.

### 5. Описание

Подробно опиши требования.

* Используй списки.
* Разделяй логические блоки.
* Описывай ожидаемое поведение системы.
* Не навязывай реализацию без необходимости.

### 6. Ожидаемый результат (Outcomes)

Опиши, что изменится после выполнения задачи.

Формулируй через конечный эффект:

* пользователь может...
* интерфейс позволяет...
* система автоматически...
* разработчику больше не требуется...

Не дублируй критерии приёмки.

### 7. Не входит в задачу (Out of scope)

Явно перечисли, что не должно реализовываться в рамках этой задачи.

Если существуют ограничения — укажи их здесь.

### 8. Критерии приёмки (Acceptance Criteria)

Список проверяемых условий.

Каждый пункт должен позволять однозначно ответить:

> Задача выполнена?

Не включай сюда пожелания, ограничения или детали реализации.

### 9. Связанные задачи (при необходимости)

Если задача является частью большого блока работ:

* перечисли предыдущие зависимости;
* укажи следующие логические шаги.

### 10. Заметки (опционально)

Используй только при необходимости.

Например:

* риски;
* ограничения;
* технические особенности;
* полезные ссылки;
* идеи на будущее.

---

## Общие правила

* Всегда начинай с проблемы, а не с решения.
* Предпочитай описание ожидаемого поведения описанию конкретной реализации.
* Не смешивай несколько крупных задач в одну.
* Если задача получается слишком большой — предложи разделить её.
* Не придумывай требования при недостатке информации — лучше задай уточняющий вопрос.
* Не повторяй одну и ту же информацию в разных разделах.
* Не описывай внутренние рассуждения, варианты реализации или процесс принятия решения, если они не нужны для постановки задачи.

---

## Форматирование

* Используй короткие абзацы.
* Каждый логический раздел отделяй пустой строкой.
* Для перечислений используй маркированные списки.
* Не делай длинных сплошных абзацев.
* Выделяй заголовки разделов.
* Используй единый стиль оформления во всех задачах.
* Избегай канцеляризмов и избыточной воды.
* Пиши так, чтобы задачу можно было быстро прочитать за 1–2 минуты.
* Сначала описывай **зачем**, затем **что нужно получить**, и только после этого **что необходимо сделать**.
* Если задача содержит UI или UX-изменения, первым шагом реализации всегда должно быть изучение текущего состояния и предложение концепции/структуры до начала разработки.

---

## Техническое замечание

Weeek MCP-сервер (`weeek_update_task`, `weeek_complete_task`) на момент 2026-08-10 не применяет изменения поля `description` и флага `isCompleted` при вызове через MCP (запрос возвращает старые данные без ошибки, `updatedAt` не меняется), хотя `priority` и `weeek_move_task` работают нормально. Из-за этого при исправлении оформления задачи иногда проще создать новую задачу с верным описанием и перенести старую в колонку «Готово» через `weeek_move_task`, чем редактировать существующую.
